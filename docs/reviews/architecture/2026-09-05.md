# Architecture Review

**Repository:** `scietex.logging` (v0.2.0)
**Date:** 2026-09-05
**Scope:** Deep architectural review of the full repository.
**Method:** All nine source modules, all eleven test files, the ten examples,
the typed-config module, and the architectural map (`docs/architecture/`) were
read and cross-verified against source by three independent read-only analyses
(core machinery, broker abstraction + backend adapters, and config/formatter/
package boundary). Line references below cite the actual current source files.

> **Note on the review file.** The prior review (`2026-09-04.md`, findings
> AR-001..AR-012, all resolved) is preserved as the historical record. This
> review is dated 2026-09-05 and continues the finding numbering from AR-013.

---

## Executive Summary

The architecture is **fundamentally sound at the layering level** and is a
small, coherent, working package. Its strongest aspects are real and worth
preserving:

- A **strict, one-way, acyclic import graph** (`config.py`/`formatter.py` are
  stdlib-only leaves; everything else chains strictly downward). No circular
  dependencies.
- A **clean machinery/backend split**: `AsyncLoggingHandler` owns the queue/
  worker/event machinery with no sink of its own; `ConsoleBackend` and the
  broker handlers are registered peers behind a uniform `register_backend`
  seam.
- A **well-formed abstract broker contract** (`connect`/`disconnect`/
  `send_message(record: dict[str, str])`), enforced via `abc.ABC`, with the
  Redis-vs-Valkey payload-shape difference being a legitimate adapter seam
  rather than a leak.
- A **restartable lifecycle** (worker factories, idempotent stop, double-start
  guard) and **bounded queues** with a drop-and-report overflow policy.

The defects that matter are concentrated in **two places**: (1) the broker
worker's failure-handling semantics, where a single transient send failure
permanently poisons the drain-status channel and a send-time connection loss
never triggers reconnection; and (2) the **typed-config subsystem**, which is
built and stored but never read at runtime — a write-only ornament that creates
a second, lossy source of truth and actively rejects valid Redis options.

There are **no CRITICAL** findings. There are **six HIGH** findings, all with
concrete, low-risk remediation paths. The highest-value single change is a
one-line correctness fix (call `task_done()` in a `finally`) that unblocks the
entire drain-status reporting story.

## Strengths (genuine, to preserve)

1. **Strict one-way acyclic import graph.** No circular dependencies; the
   layering is easy to reason about and hard to break accidentally.
2. **Clean machinery/backend split.** `AsyncLoggingHandler` is a single owner
   for the control events (`logging_accept_event`/`logging_running_event`) and
   the queue/worker lifecycle. `ConsoleBackend` and broker handlers are peers
   behind the uniform `register_backend(name, queue, worker, drain)` seam.
3. **Restartable worker-factory pattern.** Backends register zero-arg worker
   factories; `start_logging` invokes them fresh each cycle. Clean, tested.
4. **Well-formed abstract broker contract.** `connect`/`disconnect`/
   `send_message` are `@abc.abstractmethod`, enforced by `abc.ABC`
   (`test_broker_handler_is_abstract`). The `record: dict[str, str]` schema and
   the Redis (`xadd(stream, dict)`) vs Valkey (`xadd(stream, record.items())`)
   divergence are a legitimate adapter seam, not a leak.
5. **Bounded queues with drop-and-report overflow.** `queue_maxsize` (default
   10000) bounds memory; `emit` never blocks; overflow drops + reports via the
   error channel. `validate_queue_maxsize` is wired into the runtime.
6. **Dual-guard optional-import structure.** Module-level descriptive raise +
   package-level clean-import catch, with a centralized message helper
   (`optional_dependency_error`) preventing text drift.
7. **Coherent event-flag ownership.** Single owner, single-loop model; the
   off-loop `emit` guard is sufficient; the `emit` vs `stop_logging` race is
   prevented (no `await` between the accept check and `put_nowait`).
8. **Safe shared-record fan-out.** The same `LogRecord` fans into every queue;
   consumers are read-only or copy (`formatter.format` does `copy.copy`).
9. **Good testability.** No hidden module-level mutable state (only the
   `_error_logger`); backends are injectable via `register_backend`;
   `FakeBrokerHandler` covers the broker worker path without live servers.

## Issues

### HIGH

#### AR-013 — Send-failure `task_done()` poisoning causes false TIMEOUT and a permanent 5s drain
- **Severity:** HIGH
- **Evidence:** `message_broker_handler.py:150,165-170` — the worker does
  `record = await queue.get()` then, on `send_message` failure,
  `_report_error(record, exc); continue` **without** `task_done()`. The record
  was already removed by `get()`, so `continue` neither retries nor preserves
  it — it is silently lost. The only effect of withholding `task_done()` is to
  leave `Queue._unfinished_tasks` elevated forever.
- **Problem:** `queue.join()` (waited on by `drain`, `message_broker_handler.py:193`)
  can never complete once any record has failed delivery. The drain then always
  reports `DrainStatus.TIMEOUT` and the console prints a misleading timeout for
  every run with any failed delivery. Because the queue object persists across
  restarts (`start_logging` only re-schedules tasks), the counter stays poisoned
  for the handler's lifetime — every subsequent `stop_logging` burns the full
  5s and reports a false TIMEOUT even when all later sends succeed.
- **Why it matters:** the drain-status reporting channel — the whole reason the
  `results` plumbing exists — reports false timeouts, masking real ones and
  eroding trust in shutdown diagnostics. A single transient send failure has a
  permanent cost.
- **Recommendation:** call `task_done()` in a `finally` (acknowledge the
  *processing attempt*), and rely on `_report_error`/drain results for
  visibility. Do not overload `task_done()` as a redelivery signal —
  `asyncio.Queue` has no such semantics. If redelivery is wanted, re-queue for a
  bounded retry or route to a dead-letter sink.
- **Confidence:** HIGH (path visible end-to-end; the test
  `test_send_failure_surfaces_and_does_not_task_done` codifies the flawed
  mechanism and must change).

**Resolution (AR-013):** Resolved. The broker worker now calls `task_done()` in
a `finally` (`message_broker_handler.py:186-187`), so every dequeued record is
acknowledged exactly once regardless of send outcome. A failed send no longer
leaves `Queue._unfinished_tasks` elevated, so `queue.join()` in `drain`
completes and `DrainStatus.TIMEOUT` fires only when records genuinely remain.
The `send_message` contract now states a failure raises so the worker reports it
and acks the task; the record is dropped, not retried (bounded retry /
dead-letter remains a documented out-of-scope follow-up).

#### AR-014 — Shutdown timeout does not bound worker termination; a down broker hangs `stop_logging`
- **Severity:** HIGH
- **Evidence:** `async_logging_handler.py:288-290` — the `timeout` argument is
  applied only to the drain hooks (`queue.join()` in `wait_for`), never to the
  final `await asyncio.gather(*self.log_workers_tasks)`. The broker worker's
  connect-retry loop (`message_broker_handler.py:141-148`) never terminates
  when the broker is unreachable: `_report_error(None, exc); await
  asyncio.sleep(1.0); continue` indefinitely.
- **Problem:** if Redis/Valkey is down at shutdown, the drain `join()` times out
  (correctly), but the worker is then left in an infinite connect-retry loop and
  `gather` blocks indefinitely. `redis.Redis`/`GlideClient.create` have no
  bounded socket timeout by default, so this is a real hang, not theoretical.
- **Why it matters:** graceful shutdown is the feature this class exists to
  provide; it silently deadlocks in the exact failure mode (broker outage) it
  most needs to survive.
- **Recommendation:** bound the `gather` with `asyncio.wait_for` (or cancel
  workers after the drain window), and give workers an explicit termination
  signal distinct from the "drain to empty" condition so they stop retrying once
  shutdown is underway.
- **Confidence:** HIGH.

**Resolution (AR-014):** Resolved. `stop_logging` now wraps the final
`await asyncio.gather(*self.log_workers_tasks)` in `asyncio.wait_for(timeout)`
(`async_logging_handler.py:292-303`); on `asyncio.TimeoutError` it cancels
straggler tasks and re-gathers with `return_exceptions=True`, then resets
`self.log_workers_tasks = []`. A down broker can no longer hang graceful
shutdown indefinitely.

#### AR-015 — No reconnect after a send-time connection loss; a dead client is reused forever
- **Severity:** HIGH
- **Evidence:** the worker enters the connect path only when `self.client is
  None` (`message_broker_handler.py:142`); `self.client` is set to `None` only
  in `disconnect()` (`redis_handler.py:115`, `valkey_handler.py:115`), which is
  reached only at worker loop exit (`message_broker_handler.py:171-174`). There
  is no path that resets `client` on a failed send.
- **Problem:** if the connection drops mid-stream, `send_message` raises, the
  worker reports and `continue`s, but `client` is still the dead object — the
  next iteration skips reconnection and calls `xadd` on a dead client forever.
  Each queued record fails once and is dropped (AR-013), so an outage means
  total log loss until the handler is restarted. redis-py's pool does not
  auto-recover by default (`health_check_interval=0`); Valkey Glide has built-in
  reconnection, so the two adapters behave asymmetrically on the same failure.
- **Why it matters:** a logging library's core value is not silently losing logs
  through a transient outage. The reconnect machinery exists but is only
  reachable before the first successful connect.
- **Recommendation:** make send failures that indicate connectivity loss
  transition the client to a disconnected state (e.g. the worker resets
  `self.client = None` via a teardown when a send raises, so the next iteration
  reconnects), or have the adapter raise a typed "connection lost" error the
  worker maps to a reconnect. Keep Valkey's native reconnection as the baseline.
- **Confidence:** HIGH.

**Resolution (AR-015):** Resolved. The broker worker's send-failure path now
calls `self.disconnect()` (with a `self.client = None` fallback if disconnect
raises) so the next loop iteration re-enters `connect()`
(`message_broker_handler.py:179-185`). Adapter-agnostic: both Redis and Valkey
reconnect on a send-time connection loss.

#### AR-016 — Typed config is write-only: no runtime consumer, dual source of truth
- **Severity:** HIGH
- **Evidence:** `self.config.backend_config = RedisConfig(**raw)`
  (`redis_handler.py:89`) and `ValkeyConfig(addresses=...)`
  (`valkey_handler.py:91-93`) are the only write sites; grep shows **no read**
  of `.backend_config` anywhere in `src/`. `self.config` is read only during
  construction (`async_logging_handler.py:138-141`, `basic_handler.py:69-82`,
  `redis_handler.py:83-90`, `valkey_handler.py:85-92`), never again.
- **Problem:** the config dataclasses pass the *deletion test* but fail the
  *depth test* — deleting them would change nothing at runtime. Real behavior is
  driven by the parallel flat state `self.queue_maxsize`, `self.stdout_enable`,
  `self.error_handler`, `self.client_config`, `self.formatter`. The "typed
  config" is a third representation that shadows (but never governs) the actual
  state.
- **Why it matters:** it creates a false sense of a config seam. Two sources of
  truth for the same values will drift; a maintainer can "fix" a config value
  and observe no effect.
- **Recommendation:** either make `LoggingConfig` the single runtime source of
  truth (handlers read `self.config.*` at work time), or drop the typed layer
  entirely and keep the flat kwargs. Do not keep both.
- **Confidence:** HIGH (verified by grep that `backend_config` has no reader).

**Resolution (AR-016):** Resolved. `LoggingConfig` is now the single runtime
source of truth: handlers read `self.config.*` at work time, and the flat
attributes each handler exposed (`queue_maxsize`, `stdout_enable`,
`error_handler`) are read-only `@property` aliases over `self.config`
(`async_logging_handler.py:176-186`, `basic_handler.py:90-93`). Backend config
is threaded through `__init__` and assembled once at
`async_logging_handler.py:154-161`; there are no post-hoc `LoggingConfig`
rebuilds in the redis/valkey handlers. `backend_config` now has runtime readers
(e.g. the broker worker derives its identity from `self.config.service_name` /
`self.config.worker_id` at `message_broker_handler.py:173`).

#### AR-017 — `RedisConfig(**raw)` rejects valid Redis options
- **Severity:** HIGH
- **Evidence:** `RedisConfig` declares only `host/port/db` (`config.py:43-45`),
  but `raw` is passed straight to `redis.Redis(**self.client_config)`
  (`redis_handler.py:105`), which accepts many more keys (`password`, `ssl`,
  `username`, ...). `backend_config=RedisConfig(**raw)` (`redis_handler.py:89`)
  therefore raises `TypeError` on any dict containing a legitimate Redis option.
- **Problem:** the "typed" conversion both loses information and *adds a failure
  mode*: it crashes on input the underlying client happily accepts, while the
  resulting `RedisConfig` is never used.
- **Why it matters:** a user adding `redis_config={"password": ...}` gets a
  `TypeError` from a config object that does nothing. This is the worst kind of
  seam — it costs functionality and provides zero runtime value.
- **Recommendation:** if a typed Redis config is wanted, it must mirror the
  client's full option surface (or wrap the raw dict). Otherwise, pass the dict
  through and drop the typed shadow.
- **Confidence:** HIGH.

**Resolution (AR-017):** Resolved. `RedisConfig` is widened to a 39-field
frozen superset of `redis.Redis`'s plain options — `host`/`port`/`db` plus
`username`, `password`, the socket/ssl/encoding/retry/health-check/client-name/
protocol fields (`config.py:53-92`) — so `RedisConfig(**raw)` no longer rejects
a legitimate client option. Object-valued expert options (`connection_pool`,
`retry`, `credential_provider`, `cache`, `event_dispatcher`, ...) are
intentionally not modeled. The raw dict is still kept as `self.client_config`
for the `connect()` call (`redis_handler.py:84`).

#### AR-018 — Broker wire format is coupled to `ScietexFormatter` internals
- **Severity:** HIGH
- **Evidence:** `AsyncBrokerHandler._worker` builds the broker dict with
  `name = getattr(self.formatter, "worker_name", record.name)`
  (`message_broker_handler.py:156`) and `time = self.formatter.formatTime(record)`
  (`message_broker_handler.py:161-163`), while `level` and `message` are computed
  independently from the record (`:155,159`). The handler's identity
  (`service_name:worker_id`) lives only inside the *formatter*
  (`formatter.py:71`), not on the handler or config.
- **Problem:** two of four wire fields come from the formatter, two from the
  record — an inconsistent serialization seam. `setFormatter()` with a plain
  `logging.Formatter` (a supported API, `basic_handler.py:91-105`) silently
  changes broker output: `worker_name` is absent → `name` falls back to the
  logger name (identity lost), and `formatTime` degrades from ISO-8601 UTC to
  strftime. A rendering substitution should not alter the broker payload.
- **Why it matters:** the `dict[str, str]` *shape* is a clean seam, but the
  *values* are produced by reaching into one specific formatter's private
  attributes, so the contract is not stable against the supported `setFormatter`
  operation.
- **Recommendation:** derive `name`/`time` from `self.config` (identity) and the
  record (time), not from the formatter. The formatter should render; identity
  should be a first-class handler/config attribute.
- **Confidence:** HIGH.

**Resolution (AR-018):** Resolved. The broker `_worker` now derives
`name = f"{self.config.service_name}:{self.config.worker_id}"` and
`time = datetime.fromtimestamp(record.created, timezone.utc).isoformat()`
(`message_broker_handler.py:173-178`) directly from config and the record,
instead of reading `self.formatter.worker_name` / `self.formatter.formatTime`.
The broker wire format is therefore invariant under `setFormatter`: a plain
`logging.Formatter` no longer changes the `name`/`time` fields. Identity lives
on `LoggingConfig`; the formatter only renders.

### MEDIUM

#### AR-019 — Drain contract: shared mutable `results` list + implicit reverse-order semantics
- **Severity:** MEDIUM
- **Evidence:** `async_logging_handler.py:279-281` — `results: list[...] = [];
  for drain in reversed(self._drain_hooks): await drain(timeout, results)`. The
  console observes broker outcomes only via registration order (console first,
  brokers after) plus reverse iteration — emergent, undocumented, unenforced.
- **Problem:** with `stdout_enable=False`, no hook reads `results` (wasted
  bookkeeping). Adding a third backend or a second status reporter silently
  shifts semantics. The contract is only documented in prose, not enforced.
- **Recommendation:** make the coordinator (`stop_logging`) own result
  collection — hooks *return* their `BackendDrainResult` — and turn the console
  status report into an explicit post-drain observer invoked with the collected
  results.
- **Confidence:** HIGH.

**Resolution (AR-019):** Resolved. `DrainHook` is now
`Callable[[float], Awaitable[BackendDrainResult]]` — each hook returns its own
result instead of appending to a shared mutable list
(`async_logging_handler.py:46`). A new `StatusReporter` type
(`Callable[[list[BackendDrainResult]], Awaitable[None]]`, `:48`),
`_status_reporters` list, and `register_status_reporter()` method
(`:219-232`) were added. `stop_logging` iterates `_drain_hooks` in registration
order, collects the returned results, then invokes each status reporter with
the full list (`:334-338`). `AsyncBrokerHandler.drain` and
`ConsoleBackend.drain` each return a `BackendDrainResult`
(`message_broker_handler.py:210`, `console_backend.py:107`); the console's
status reporting moved to a new `ConsoleBackend.report_status(results)`
(`console_backend.py:130`), which `AsyncBaseHandler` registers as a status
reporter (`basic_handler.py:88`). The reverse-registration-order coupling is
gone.

#### AR-020 — Queues are never cleared across restarts, contradicting the "clean queue" contract
- **Severity:** MEDIUM
- **Evidence:** the class docstring claims "each start schedules fresh tasks from
  a clean queue" (`async_logging_handler.py:60-61`), but `register_backend`
  stores the queue once and `start_logging` only recreates the *tasks*
  (`:204-206`). The queues are never recreated or cleared.
- **Problem:** if a prior cycle timed out with records still queued, those
  records are replayed in the next cycle, risking duplicate broker delivery.
- **Recommendation:** either clear/drop undelivered records on stop (and say
  so), or correct the documentation to state explicitly that undrained records
  are replayed on restart. Choose the semantics deliberately.
- **Confidence:** HIGH.

#### AR-021 — Console worker has no error channel
- **Severity:** MEDIUM
- **Evidence:** `console_backend.py:92-100` — only `asyncio.TimeoutError` is
  caught. `self.formatter.format(record)` or `sys.stdout.write` can raise (e.g.
  `BrokenPipeError` on a closed pipe), terminating the task and surfacing via the
  `gather` in `stop_logging` or as an unretrieved task exception.
- **Problem:** inconsistent with the broker worker, which routes every failure
  class through `_report_error`. The console is the *always-on* backend; a
  broken stdout can crash shutdown or silently kill the console worker.
- **Recommendation:** wrap format/write in the same error-reporting discipline
  as the broker worker, or accept an injected stream/error handler so the
  console backend is symmetric with broker backends.
- **Confidence:** HIGH.

#### AR-022 — Connect retry loop has no backoff, max attempts, or degradation signal
- **Severity:** MEDIUM
- **Evidence:** `message_broker_handler.py:141-148` — a fixed 1-second
  error-report loop indefinitely; no exponential backoff, jitter, max-retry, or
  circuit breaker. The worker does not drain while disconnected (correct), so
  records accumulate to `queue_maxsize` then `emit` drops them.
- **Problem:** no way to distinguish a transient outage from a permanent one, and
  no bound on error-channel volume (spams ~3600×/hour during a long outage).
- **Recommendation:** add capped exponential backoff with jitter and/or a
  "backend unhealthy" state the handler can expose; surface the outage as a
  single transition event rather than a per-second repeat.
- **Confidence:** HIGH.

#### AR-023 — `backend_config: Any` is an untyped hole; config held in two representations
- **Severity:** MEDIUM
- **Evidence:** `backend_config: Any | None = None` (`config.py:30`) — the
  docstring names `RedisConfig`/`ValkeyConfig`/`None` but the type is `Any`,
  erasing type checking at exactly the discriminated-union point. Redis keeps
  both `self.client_config: dict` and `self.config.backend_config`; Valkey keeps
  both `self.client_config: GlideClientConfiguration` and a projected
  `ValkeyConfig`.
- **Problem:** the typed side earns nothing at type-check time (`Any`) and is
  strictly weaker than the raw side. The `frozen=True` `LoggingConfig` forces
  each subclass to reconstruct the whole config post-hoc just to attach
  `backend_config`.
- **Recommendation:** use a real union (`RedisConfig | ValkeyConfig | None`) or
  delete the field; thread backend config through `__init__` rather than
  reconstructing `LoggingConfig` post-hoc.
- **Confidence:** HIGH.

**Resolution (AR-023):** Resolved. `backend_config` is now typed
`RedisConfig | ValkeyConfig | None` (`config.py:33`), so the discriminated-union
point is type-checked. Backend config is threaded through `__init__` and
assembled once into `LoggingConfig` at `async_logging_handler.py:154-161`; the
redis/valkey handlers no longer rebuild `LoggingConfig` post-hoc to attach
`backend_config` (`redis_handler.py:81`, `valkey_handler.py:83`). Each handler
still keeps its raw `client_config` (dict for Redis, `GlideClientConfiguration`
for Valkey) for `connect()`.

#### AR-024 — `AsyncLoggingHandler.__init__` hard-codes `ScietexFormatter`; no formatter injection
- **Severity:** MEDIUM
- **Evidence:** `self.formatter = ScietexFormatter(service_name=..., worker_id=...)`
  (`async_logging_handler.py:140-142`); no handler constructor accepts a
  `formatter=` kwarg. Substitution is only possible post-hoc via `setFormatter`.
- **Problem:** the machinery base is not formatter-agnostic; it bakes in one
  concrete formatter. Post-hoc substitution has hidden broker side effects
  (AR-018).
- **Recommendation:** accept an optional `formatter` at construction (defaulting
  to `ScietexFormatter`), and decouple broker serialization from the formatter
  (AR-018) so the swap is safe.
- **Confidence:** HIGH.

#### AR-025 — Backend config-input asymmetry: dict vs third-party object
- **Severity:** MEDIUM
- **Evidence:** Redis takes `redis_config: dict | None` (`redis_handler.py:43`);
  Valkey takes `valkey_config: GlideClientConfiguration | None`
  (`valkey_handler.py:43`), a third-party type that leaks across the package
  boundary.
- **Problem:** the two sibling backends have inconsistent config seams. A caller
  targeting both backends must know two unrelated shapes, and the Valkey
  signature exposes `glide` types in a public handler constructor.
- **Recommendation:** define one package-level config story for backends (e.g.
  both accept a dict or a package-owned config object), and translate to vendor
  types *inside* `connect()`.
- **Confidence:** HIGH.

#### AR-026 — `level_abbreviation` lives in the formatter module but is a serialization primitive
- **Severity:** MEDIUM
- **Evidence:** defined in `formatter.py:10`, used by `ScietexFormatter.format`
  (`formatter.py:110`) and imported by `AsyncBrokerHandler`
  (`message_broker_handler.py:12`, used at `:155`).
- **Problem:** a pure level→string mapping is owned by the console-rendering
  module, so the broker module imports the formatter module for a concern that
  isn't formatting. This is the compile-time edge the broker's formatter
  coupling (AR-018) rides on.
- **Recommendation:** move `level_abbreviation` to a neutral leaf (e.g.
  `config.py` or a dedicated `_levels.py`) so both formatter and broker depend
  on it, rather than the broker depending on the formatter.
- **Confidence:** HIGH.

#### AR-027 — Broad `except ImportError: pass` can hide genuine failures
- **Severity:** MEDIUM
- **Evidence:** `__init__.py:116-127` wraps the backend imports in
  `try/except ImportError: pass`. The descriptive message (`config.py:67-72`) is
  only reachable via a *direct* `import scietex.logging.redis_handler`.
- **Problem:** the guard swallows any `ImportError` raised while importing a
  backend module — not just the missing-optional-client case — including a bug
  or a missing transitive dependency inside `redis_handler.py`. A user writing
  `from scietex.logging import AsyncRedisHandler` with Redis uninstalled gets
  the unhelpful stdlib "cannot import name" rather than the crafted message.
- **Recommendation:** re-raise any `ImportError` whose `name` is not the expected
  optional dependency, and/or expose a module-level `__getattr__` raising the
  descriptive error on access to `AsyncRedisHandler`.
- **Confidence:** HIGH.

#### AR-028 — `register_backend` has no duplicate-name validation
- **Severity:** MEDIUM
- **Evidence:** `async_logging_handler.py:178-181` — `self.log_queues[name] =
  queue` overwrites on duplicate, but `log_worker_factories.append(worker)` and
  `_drain_hooks.append(drain)` still append. Names are hardcoded literals
  (`"redis"`, `"valkey"`, `"console"`).
- **Problem:** two backends under one name silently overwrite the queue while
  doubling the workers and drain hooks, desynchronizing `log_queues` from the
  parallel lists. In-package the fixed set is safe; the risk is to third-party
  `AsyncBrokerHandler` subclasses (the documented extension point).
- **Recommendation:** detect duplicate names in `register_backend` (raise or
  assert), or key the workers/hooks by name too.
- **Confidence:** HIGH.

#### AR-029 — Redis end-to-end test lacks a skip guard (testability asymmetry)
- **Severity:** MEDIUM
- **Evidence:** `tests/test_redis_handler.py:14-69`
  (`test_redis_handler_logs_to_stream`) connects to `localhost:6379` with no
  `pytest.mark.skipif`, while `tests/test_valkey_handler.py:24-27` guards the
  equivalent test with `_valkey_server_reachable()`. Both rely on
  `await asyncio.sleep(1)` then assert (timing-fragile).
- **Problem:** `uv run pytest` fails on any machine/CI without a Redis server,
  whereas the Valkey test cleanly skips. The suite's pass/fail depends on
  ambient infrastructure.
- **Recommendation:** apply the same reachability guard to the Redis e2e test,
  and replace fixed `sleep(1)` waits with predicate polling (`_wait_for` already
  exists in the base tests).
- **Confidence:** HIGH.

### LOW

#### AR-030 — Formatter state is duplicated (captured vs dynamic)
- **Severity:** LOW
- **Evidence:** `ConsoleBackend` captures the formatter at construction;
  `AsyncBaseHandler.setFormatter` (`basic_handler.py:91-105`) manually re-syncs
  `self._console_backend.formatter = fmt`. The broker worker reads
  `self.formatter` dynamically.
- **Problem:** two sources of truth for "the active formatter"; the override's
  maintenance burden grows with each future capturing backend.
- **Recommendation:** standardize on dynamic reads of the handler's formatter
  (the broker pattern), or have backends hold a single shared formatter
  reference object.
- **Confidence:** HIGH.

#### AR-031 — `_report_error` silently swallows `error_handler` exceptions with no fallback
- **Severity:** LOW
- **Evidence:** `async_logging_handler.py:304-309` — `try: self.error_handler(
  record, exc); except Exception: pass` with no fallback to the module logger.
- **Problem:** a buggy user-supplied `error_handler` silently loses all error
  telemetry — including the overflow-drop reports, which are the *only*
  visibility into `emit`'s silent drop policy.
- **Recommendation:** fall back to the module logger when the callback raises.
- **Confidence:** HIGH.

#### AR-032 — `disconnect()` is not in a `finally`; cancellation leaks the client
- **Severity:** LOW
- **Evidence:** `message_broker_handler.py:171-174` (disconnect after the loop,
  in `try/except Exception`); `async_logging_handler.py:288-290` gathers workers
  without cancelling them. `asyncio.CancelledError` is a `BaseException`, not
  caught by `except Exception`.
- **Problem:** if the event loop tears down before `stop_logging`, the worker can
  be cancelled at `await send_message` — the in-flight record is dequeued and
  un-acked, and `disconnect()` never runs, leaking the client. A failed
  `disconnect()` also leaves a stale client that never reconnects on restart.
- **Recommendation:** wrap the worker body so `disconnect()` runs in a `finally`,
  and make disconnect idempotent (reset `self.client = None` in a `finally`).
- **Confidence:** HIGH.

**Resolution (AR-032):** Resolved. The broker worker's connect-retry + drain
loop is now wrapped in `try: ... finally:` so `disconnect()` runs (and
`self.client` is unconditionally reset to None) on both normal exit and
cancellation (`message_broker_handler.py:142,188-197`). This was required
because AR-014's gather-bound cancel reaps workers idling in `queue.get()`
before they reach the natural end of the loop.

#### AR-033 — Redis `connect()` leaks the locally created client when `ping()` fails
- **Severity:** LOW
- **Evidence:** `redis_handler.py:104-107` — `client = await redis.Redis(...);
  await client.ping(); self.client = client`. If `ping()` raises, `self.client`
  stays `None` (correct) but the local `client` and its pool are abandoned
  without `aclose()`. This runs every second during an outage (AR-022).
- **Recommendation:** close the local client in the failure path before
  re-raising.
- **Confidence:** HIGH.

#### AR-034 — `send_message` silently no-ops when `self.client is None`
- **Severity:** LOW
- **Evidence:** `redis_handler.py:127-128`, `valkey_handler.py:128-129` —
  `if self.client is not None: await xadd(...)`. When `client is None`,
  `send_message` returns normally, so the worker calls `task_done()` and the
  record is silently acknowledged as delivered when nothing was sent.
- **Problem:** violates the documented "failure must raise" contract
  (`message_broker_handler.py:119`). Currently defensive dead code (the worker
  connects before sending), but a latent trap under any future ordering change.
- **Recommendation:** make `send_message` raise (or return a failure signal) when
  there is no client, or assert `client is not None` as a precondition.
- **Confidence:** HIGH.

#### AR-035 — Public surface is inconsistent and partially leaks internals
- **Severity:** LOW
- **Evidence:** `__all__` exports `ConsoleBackend` (`__init__.py:112`), an
  internal sink only `basic_handler.py` constructs, while
  `LoggingConfig`/`RedisConfig`/`ValkeyConfig` are *not* exported (tests import
  them from submodules). `AGENTS.md`'s "Public API" section omits
  `AsyncLoggingHandler` and `ConsoleBackend`, contradicting the real `__all__`.
- **Recommendation:** decide deliberately — export the config types (if the
  config seam is kept) and demote `ConsoleBackend` to internal, then align
  `AGENTS.md`.
- **Confidence:** HIGH.

#### AR-036 — `optional_dependency_error` is a packaging concern in the config module
- **Severity:** LOW
- **Evidence:** `config.py:67-72` defines the import-error message helper;
  consumed only by `redis_handler.py:8` and `valkey_handler.py:8`.
- **Problem:** it is not configuration; it landed in `config.py` because that is
  the shared stdlib-only leaf. A defensible placement, but it muddies the
  module's single responsibility.
- **Recommendation:** acceptable as-is; if a neutral leaf already exists for
  `level_abbreviation` (AR-026), this helper could share it.
- **Confidence:** HIGH.

## Cross-Cutting Analysis

Four themes recur across the findings:

1. **Worker failure-handling semantics are the load-bearing defect cluster**
   (AR-013, AR-014, AR-015, AR-022, AR-032, AR-033). All live in the broker
   worker's connect/send/disconnect error paths. A single coherent redesign of
   worker failure handling — ack the processing attempt unconditionally, reset
   the client on connectivity loss, bound the connect retry, run disconnect in a
   `finally` — addresses most of the HIGH findings at once.

2. **The config subsystem is a write-only ornament creating a dual source of
   truth** (AR-016, AR-017, AR-023, AR-025). The decision is binary: make
   `LoggingConfig` the single runtime source of truth, or drop the typed layer
   and keep the flat kwargs. Keeping both guarantees drift.

3. **The broker wire format is coupled to formatter internals** (AR-018,
   AR-026, AR-024). Handler identity (`service_name:worker_id`) should be a
   first-class handler/config attribute, not recovered from a renderer. Fixing
   this should precede adding formatter injection, or the silent-drift hazard
   widens.

4. **The drain/status-reporting mechanism is fragile** (AR-019, AR-020). The
   shared-mutable-results + reverse-order contract and the never-cleared queues
   both make restart and multi-backend behavior harder to reason about than it
   needs to be.

## Architectural Recommendations

### Priority 1 (correctness defects — fix first)

1. **AR-013** — call `task_done()` in a `finally` in the broker worker. One-line
   correctness fix; unblocks the drain-status reporting story. Update
   `test_send_failure_surfaces_and_does_not_task_done` and
   `test_restart_after_drain_timeout`, which encode the flawed model.
2. **AR-014** — bound the worker `gather` with `wait_for` (or cancel workers
   after the drain window) and give workers an explicit stop signal distinct
   from drain-to-empty. Fixes the shutdown hang on a down broker.
3. **AR-015** — reset/disconnect the client on a send-time connectivity loss so
   the worker re-enters the `connect()` path. Fixes total log loss during an
   outage.

### Priority 2 (structural — decide and refactor)

4. **AR-016/AR-017/AR-023** — decide the config strategy: make `LoggingConfig`
   the single runtime source of truth, or drop the typed config classes. If
   kept, `RedisConfig` must mirror the full client option surface and
   `backend_config` must be a real union, not `Any`.
5. **AR-018** — decouple broker schema production from `ScietexFormatter`
   internals; make identity a first-class handler/config attribute.
6. **AR-019** — make the coordinator own result collection (hooks return their
   `BackendDrainResult`); turn the console status report into an explicit
   post-drain observer.

### Priority 3 (hardening — as budget allows)

7. **AR-020** — resolve queue-clear-vs-replay semantics and align the docstring.
8. **AR-021** — give the console worker an error channel (symmetric with broker).
9. **AR-022** — add capped exponential backoff + jitter to the connect retry.
10. **AR-024** — add a `formatter=` construction kwarg (after AR-018).
11. **AR-025** — unify the backend config-input story.
12. **AR-026** — relocate `level_abbreviation` to a neutral leaf.
13. **AR-027** — tighten the `__init__.py` guard to re-raise non-optional
    `ImportError`s.
14. **AR-028** — add duplicate-name validation to `register_backend`.
15. **AR-029** — add a Redis skip guard mirroring the Valkey one.
16. **AR-030..AR-036** — the LOW items (formatter-state dedup, error-handler
    fallback, disconnect-in-finally, connect leak, send_message precondition,
    public-surface decision, helper locality).

## Suggested Target Architecture

The current architecture is close to the target; the recommendations are
refinements, not a redesign. The target state:

```
logging.Handler
    └── AsyncLoggingHandler          (pure machinery; single source of truth:
                                      reads self.config.* at work time)
        ├── AsyncBaseHandler         (registers ConsoleBackend peer)
        │     └── AsyncBrokerHandler (abc.ABC)
        │           ├── AsyncRedisHandler
        │           └── AsyncValkeyHandler
        └── ConsoleBackend           (peer console sink)
```

Key target properties:

- **Worker failure handling is coherent**: every dequeued record is acked
  (`task_done()` in `finally`); connectivity loss resets the client so the next
  iteration reconnects; the connect retry is bounded with backoff; `disconnect`
  runs in a `finally` and is idempotent.
- **Config is a single source of truth**: `LoggingConfig` (with a faithful,
  typed `backend_config`) is read at work time, not shadowed by parallel flat
  state.
- **Identity is first-class**: `service_name:worker_id` lives on the
  handler/config, and the broker builds its payload from config + record, not
  from the formatter. The formatter only renders.
- **Drain reporting is explicit**: `stop_logging` collects each backend's
  `BackendDrainResult`; the console is an explicit post-drain observer, not a
  hook reading a shared list mid-iteration.

## Migration Strategy

The findings are largely independent and can be landed incrementally, each as a
small, tested change:

1. **AR-013** first (one-line, unblocks drain reporting). Update the two tests
   that encode the flawed model.
2. **AR-014 + AR-015** together (both touch the broker worker's loop and error
   paths). Add a bounded-connect-retry test and a reconnect-on-send-failure
   test.
3. **AR-018** (decouple broker from formatter) before **AR-024** (formatter
   injection), so the swap is safe.
4. **Config decision (AR-016/017/023)** as a focused refactor with its own test
   pass; update `test_config.py`, `test_redis_handler.py`, and
   `test_valkey_handler.py`, which currently encode the write-only shadow.
5. The remaining MEDIUM/LOW items as hardening, each independently verifiable.

Each step keeps the full suite green (`uv run pytest -q`, `uv run ruff check .`,
`uv run ty check src/scietex/logging/`).

## Open Questions

1. **Config strategy**: single-source-of-truth `LoggingConfig`, or drop the
   typed layer? This is the largest open decision and drives AR-016/017/023/025.
2. **Send-failure policy**: ack-and-drop (with `_report_error` visibility) vs
   bounded re-queue vs dead-letter? AR-013's fix depends on this. Re-queueing
   must bound retries to avoid a poison-message infinite loop.
3. **Reconnect semantics**: should a send failure always reset the client, or
   only connectivity-class failures? Must not fight Valkey Glide's native
   reconnection/HA.
4. **Queue semantics across restart**: clear undelivered records on stop, or
   document replay? AR-020.
5. **Public surface**: export the config types and demote `ConsoleBackend`, or
   keep the current `__all__`? AR-035.
